# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

This is a personal [Klipper](https://www.klipper3d.org/) 3D printer configuration repo for two printers, not a software project. There is no build, lint, or test tooling — changes are validated by restarting Klipper/Moonraker on the printer's host and observing behavior, or by careful manual review of G-code macro logic. There are no automated tests to run.

## Layout

- `printers/klipper-vs-146/` — SKR Mini E3, corexz kinematics, BLTouch probe, Fluidd UI.
- `printers/klipper-v0/` — Voron 0.2 (SKR Pico + LDO Picobilical toolhead board), corexy kinematics, sensorless XY homing, Mainsail UI.
- `macros/` — shared, hardware-agnostic gcode macros and client-macro config (`debug.cfg` / `DUMP_PARAMETERS`, `prime_line.cfg` / `PRIME_LINE`, `print_start.cfg` / `PRINT_START`, `heat_soak.cfg` / `HEAT_SOAK`, `notify.cfg` — no-op defaults for all five `*_NOTIFY` macros, `filament.cfg` / `_LOAD_FILAMENT`+`_UNLOAD_FILAMENT`, `mainsail.cfg` — see below). Each printer directory has a `macros` symlink to this directory, included as `[include macros/<file>.cfg]`. Only add files here that have zero hardware coupling (no pin references, no printer-specific parking/heating values) — everything else belongs in the printer's own directory; most files here are pure `[gcode_macro]` definitions, but `mainsail.cfg` is the one exception that also carries a few generic, equally hardware-agnostic extras sections (`[virtual_sdcard]`, `[pause_resume]`, etc.) alongside its macros. The two printers' print-end macros are intentionally _not_ unified — they differ enough in hardware to stay printer-local. `PAUSE`/`RESUME`/`CANCEL_PRINT` are unified at the vendor level instead: both printers now include the same vendored `macros/mainsail.cfg` client macro pack — the Alex Zellner `_CLIENT_VARIABLE`-based macro set (runout-sensor awareness, idle-timeout restore, temp restore, configurable park/retract, pause-at-layer; its `RESUME`/`PAUSE`/`CANCEL_PRINT` chain from the `[pause_resume]` built-ins via `rename_existing: RESUME_BASE` etc.) — rather than each hand-rolling its own (it's UI-agnostic — klipper-vs-146 still uses Fluidd as its actual web UI). Genuinely do not hand-edit this file, it's meant to stay a clean copy of the upstream template — upstream is [mainsail-crew/mainsail-config](https://github.com/mainsail-crew/mainsail-config)'s `client.cfg` (the repo renamed it from `mainsail.cfg` in 2023; this repo keeps the old filename since that's already what both printers' includes/docs reference). Confirmed byte-identical to upstream as of the `_CLIENT_LINEAR_MOVE` addition (2024-11-24) — if re-syncing from upstream later, note that this repo's copy does **not** include an `[exclude_object]` section even though an earlier local copy briefly had one; that support now lives as an explicit `[exclude_object]` in each printer's own `printer.cfg` instead (re-copying the file wholesale from upstream is safe and won't lose it). It ships its own extension point instead: a fully-commented-out `[gcode_macro _CLIENT_VARIABLE]` template (with `variable_user_resume_macro`/`variable_runout_sensor`/etc. hooks) that users are meant to copy into `printer.cfg` and customize. Each printer's own `printer.cfg` defines its own **partial** `_CLIENT_VARIABLE` — only the specific variables it needs, not the full template, since every other `client.*` lookup in `mainsail.cfg` already falls back gracefully via `|default(...)` when a variable isn't set: klipper-v0 sets just `user_resume_macro: "RESUME_NOTIFY"`; klipper-vs-146 sets that plus `runout_sensor: "filament_motion_sensor filament_sensor"` (aborts `RESUME` if no filament is detected — this replaced vs-146's old manual `SET_FILAMENT_SENSOR` enable/disable around pause/resume/cancel, which had no equivalent in `mainsail.cfg` and was dropped rather than replicated). Don't copy the rest of the template in without a reason; it'd silently change working `PAUSE`/`CANCEL_PRINT`/park defaults. Never add a same-named `printer.cfg` override of `PAUSE`/`RESUME`/`CANCEL_PRINT` — see the `rename_existing` warning below for why that silently corrupts `mainsail.cfg`'s real logic instead of chaining onto it; use the `_CLIENT_VARIABLE` hooks instead.

  `PRINT_START` and `HEAT_SOAK` are the exceptions — both shared, with any genuinely hardware-specific step delegated to a printer-local macro that the shared one calls unconditionally. `PRINT_START` heats the bed itself (`M190`, generic — both printers have `[heater_bed]`), then calls: `HEAT_SOAK` (waits for the shared `temperature_sensor chamber_temp` to reach `CHAMBER`/`CHAMBER_MINIMAL`, skipped if neither is set above 0 — a pure blocking wait with no timeout, so a target the chamber can't reach will hang the print), then re-homes Z (`G28 Z`, generic — both printers' homing setups handle a Z-only home safely: klipper-vs-146's `[safe_z_home]` repositions to its own safe XY point first, klipper-v0's `[homing_override]` already treats `G28 Z` as Z-only) since frame thermal expansion during the soak can drift the cold Z homing reference taken earlier in this same macro, `CHECK_BED_LEVEL` (screw tilt probing — real on klipper-vs-146 via its `SCREWS_TILT_CALCULATE`, a no-op on klipper-v0, no probe), and `LOAD_BED_MESH` (loading a saved mesh profile — real on klipper-vs-146, a no-op on klipper-v0, no `[bed_mesh]` configured). New printer-specific steps inside a shared macro should follow this same pattern: call a same-named macro unconditionally, then give every printer an implementation (even if a no-op) rather than branching on printer identity inside the shared file.

  Status notification (LED + console + Telegram) follows a public/private split. Public macros are named for what they indicate, not their color — `HEAT_SOAK_NOTIFY` (called from `HEAT_SOAK`), `PRINT_START_NOTIFY` (called from `PRINT_START`), `PRINT_END_NOTIFY` (called from each printer's own `PRINT_END`), `ATTENTION_NOTIFY` (called from any macro that pauses for manual user input — the shared `M600` (see below), plus klipper-vs-146's own `SCREWS_TILT_CALCULATE`; klipper-v0 has no other pause point of its own yet), `RESUME_NOTIFY` (called via `macros/mainsail.cfg`'s `user_resume_macro` hook — see above — rather than a same-named `RESUME` override). All five no-op defaults live together in `notify.cfg` regardless of which macro calls them — `PRINT_START_NOTIFY`/`HEAT_SOAK_NOTIFY` are called from the shared `PRINT_START`/`HEAT_SOAK`, while `PRINT_END_NOTIFY`/`ATTENTION_NOTIFY`/`RESUME_NOTIFY` are called from printer-local macros — so this is the one place to look for the full set. Each is safe to call from any printer. Both printers now have a light and override every one of them by simply **redefining the macro** — same section name, no `rename_existing` — to call `_LED_SET NAME=<color> LED=<their light>` — a single **private**, underscore-prefixed, shared entry point (also in `notify.cfg`; the leading underscore is Klipper's own convention for hiding a macro from the web UI's macro panel, signaling "internal helper, not meant to be invoked directly"). Passing `LED=` as a param is what lets this stay a single shared macro instead of a per-printer copy — klipper-vs-146 passes `LED=enclosure` (RGB hardware; the unused `WHITE` component is harmless to pass), klipper-v0 passes `LED=bed_light` (RGBW).

  **Do not add `rename_existing` to these overrides.** Klipper's config loader merges same-named `[gcode_macro X]` sections across every included file into one final section (`configfile.py` builds the parser with `strict=False` specifically so overrides "apply linearly as they do within a single file") — a later block's `gcode:`/`description:` simply overwrite the earlier block's, which is exactly the full-replacement behavior these overrides want, no chaining mechanism required. `rename_existing` only makes sense when overriding a macro that has genuinely distinct content underneath that must still run — and since the same merge applies there too, a second `[gcode_macro SAME_NAME]` block doesn't produce two chainable objects, it collapses into the _one_ merged section Klipper actually loads. Concretely: `rename_existing` only works safely when the name being renamed is a Klipper **built-in** (registered by an extras module — e.g. `PAUSE`/`RESUME`/`CANCEL_PRINT`/`SET_PRINT_STATS_INFO` from `[pause_resume]`, `SCREWS_TILT_CALCULATE` from `[screws_tilt_adjust]`, `BED_MESH_CALIBRATE` from `[bed_mesh]`) — those are registered independently, before any config-file `[gcode_macro]` merging happens, so there's a real separate registration for the override to find at `klippy:connect`. A same-named `[gcode_macro RESUME]` override was tried here once to reset the LED on resume and had to be reverted after redeploying to klipper-v0 exposed the bug: the override's section name collided with `mainsail.cfg`'s real `RESUME` macro, silently discarding its actual resume logic in the merge — not a crash, a silent regression, only caught because that redeploy was the first time this config had ever actually been parsed by Klipper. `RESUME_NOTIFY` is now wired up correctly instead, without a same-named override — via `macros/mainsail.cfg`'s `user_resume_macro` hook, described above.

  Color scheme (deliberately tight — same meaning on both printers): `blue` = actively running (`PRINT_START_NOTIFY`), `orange` = heating/warming up, not a problem (`HEAT_SOAK_NOTIFY`), `yellow` pulsing = needs your attention (`ATTENTION_NOTIFY`), `green` = done (`PRINT_END_NOTIFY`). `red` is intentionally unused by any indicator right now — reserved for a real fault, so it doesn't get diluted by reuse elsewhere (e.g. don't repurpose it for heating or any other non-error state). `off`/`white` remain general-purpose presets in `_LED_COLOR`, not tied to a print-lifecycle indicator.

  `_LED_SET` normally sets a solid color via `_LED_COLOR` (the lower-level macro holding the actual name→RGBW lookup and `SET_LED` call — `_LED_SET` always cancels any in-progress pulse first, then delegates). Pass `PULSE=1` (used by both printers' `ATTENTION_NOTIFY`) for a slow breathing fade instead of a solid color: since gcode macros run synchronously and can't block for the life of a pause, the actual animation lives in `[delayed_gcode _LED_PULSE]`, a self-rescheduling timer (fires every 0.15s, `initial_duration: 0` so it's dormant until triggered) that ramps `_LED_COLOR`'s `BRIGHTNESS` param up and down across a 24-step triangle wave (~7s per full breath) and reschedules itself via `UPDATE_DELAYED_GCODE`. Its state (which LED, which color, current step/direction) persists between ticks in `_LED_PULSE_STATE`, a `[gcode_macro]` used purely as variable storage (set via `SET_GCODE_VARIABLE`, read via `printer["gcode_macro _LED_PULSE_STATE"]`) since `[delayed_gcode]` can't receive params at trigger time. `RESUME_NOTIFY` (solid `blue`, no `PULSE`) cancels any in-progress pulse the same way, so resuming from an `ATTENTION_NOTIFY` pause clears it immediately.

  Every LED change also notifies the console and Telegram, so the two stay in sync rather than requiring each call site to remember a separate `RESPOND`. This lives in `_LED_SET` itself: it takes an optional `MSG`, and when present emits both a plain `RESPOND` (console) and a `RESPOND PREFIX=tgnotify` (Telegram, via moonraker-telegram-bot). Because it's keyed off `_LED_SET`, the notification only fires on a printer where the `*_NOTIFY` override actually has a light to set — on the no-op defaults nothing changed, so nothing is said. Most `_NOTIFY` public macros just forward a caller-supplied `MSG` straight through to `_LED_SET` (e.g. `PRINT_START` calls `PRINT_START_NOTIFY MSG="Print started."`; `M600` calls `ATTENTION_NOTIFY MSG="Filament Change (M600) needs your attention."`) — this is what lets `ATTENTION_NOTIFY`, which is called from more than one context (`M600`, klipper-vs-146's `SCREWS_TILT_CALCULATE`), say something different each time despite sharing one override. `PRINT_START_NOTIFY` is likewise called twice from `PRINT_START` with two different messages: once at the very top (`MSG="Print started."`, before homing/heating begin) and once right before `PRIME_LINE` (`MSG="Printing started."`, after homing/heat-soak/leveling all finish, just before priming and the sliced print body run) — the second call exists because `HEAT_SOAK_NOTIFY` (orange) runs in between and would otherwise leave the LED on orange for the rest of the print; re-calling `PRINT_START_NOTIFY` restores blue right as printing actually begins. `RESUME_NOTIFY` is the one exception: `mainsail.cfg`'s `user_resume_macro` hook invokes it bare, with no way to pass a param, so its override states a static `MSG="Print resumed."` directly rather than forwarding one. This replaces what used to be ad hoc, easy-to-forget `RESPOND PREFIX=tgnotify` lines duplicated next to individual `*_NOTIFY` calls (`PRINT_END`, `SCREWS_TILT_CALCULATE`, `M600`) — those are gone now that the message travels with the LED call itself.

  New status points should follow this same split: add a public `_NOTIFY` macro with a shared no-op default, and let printers with a light override it — by plainly redefining the same-named macro, **not** `rename_existing` — to call `_LED_SET NAME=... LED=... MSG=...` (forwarding the caller's `MSG` param, or a static one if the call site can't pass params — see above; adding a new color preset is a one-line dict entry in `_LED_COLOR`, shared by every printer) — never call `SET_LED` or `_LED_COLOR` directly from a public macro.

  `LOAD_FILAMENT`/`UNLOAD_FILAMENT` use a third, distinct sharing pattern — neither the no-op-default delegation above nor the vendored-file approach, since here the actual _logic_ (wait for temp, feed/purge, retract) is genuinely identical between printers and only the _numbers_ (distances, speeds) are hardware-specific. `filament.cfg` holds the shared engine, `_LOAD_FILAMENT`/`_UNLOAD_FILAMENT` (private, underscore-prefixed — takes `LENGTH`/`LOAD_SPEED`/`PRIME_LENGTH`/`PRIME_SPEED`/`RETRACT_AFTER` or `RETRACT_LENGTH`/`RETRACT_SPEED`/`PURGE_LENGTH`/`PURGE_SPEED`, all required distances explicit — no printer-specific defaults baked into the shared file, since there's no sane universal default for "how far is it from the extruder gear to the nozzle"). `_LOAD_FILAMENT` chunks `LENGTH` into however many equal moves are needed to stay at or under this printer's own `[extruder]` `max_extrude_only_distance` (read live via `printer.configfile.settings.extruder.max_extrude_only_distance` — no safety margin needed, Klipper's own check in `kinematics/extruder.py` is strictly-greater-than, so a move exactly at the configured limit is accepted) — that's a Klipper hard limit per single extrude-only move, not something either printer's wrapper should have to know about or compute; `MAX_CHUNK` is exposed only as an override if ever needed. `_LOAD_FILAMENT`'s `RETRACT_AFTER` is the one exception with a real default: `mainsail.cfg`'s own `_CLIENT_VARIABLE.unretract` (the amount `RESUME`'s `_CLIENT_EXTRUDE` will un-retract), so the net filament position stays consistent across pause→load→resume on **both** printers automatically — pass `RETRACT_AFTER=0` to disable. (This used to be vs-146-only, reading a `PAUSE.extrude` variable that only existed on the old `client_macros.cfg`'s `PAUSE` — after the `mainsail.cfg` switch that lookup silently resolved to `Undefined|float` → `0.0`, quietly dropping the retract. Caught during a later review, not a redeploy — a reminder that `printer["gcode_macro X"].some_variable` lookups need re-checking whenever the macro being read from changes.) Each printer's own `printer.cfg` defines the public `LOAD_FILAMENT`/`UNLOAD_FILAMENT` as a thin wrapper supplying its own literal `LENGTH`/speeds and calling the shared engine — klipper-vs-146 loads ~500mm total (chunked automatically into several sub-100mm moves), klipper-v0 loads 30mm in one move; neither wrapper thinks about chunking at all. Both wrappers preserve `EXTRUDER=` for any existing callers (M600 prompts, UI buttons); klipper-vs-146's `LOAD_FILAMENT` also still accepts `E=` (now meaning total length, not per-chunk size as it briefly did mid-refactor). This is the pattern to reach for when unifying a macro whose _logic_ is identical but whose _numbers_ are physical/hardware-specific — don't force it into the no-op-delegation pattern, and don't try to invent a "reasonable universal default," require the caller to state it. `_LOAD_FILAMENT`/`_UNLOAD_FILAMENT` set `M83` (relative extrude) and deliberately do **not** switch back to `M82` on exit — see the "Relative vs. absolute extrude" note below for why that's the actually-correct choice here, not an oversight.

  `filament.cfg` also holds a fully shared `M600` (plain, single definition — not per-printer, not delegated, since by the time it was extracted every piece it calls was already safe on both printers): `PAUSE` (parks the toolhead first, from `mainsail.cfg`) → `UNLOAD_FILAMENT {rawparams}` (each printer's own wrapper, forwarding any `E=`/`EXTRUDER=` the caller passed) → `ATTENTION_NOTIFY` → a `tgnotify`/UI resume prompt. klipper-v0 gets `M600` for free through its existing `[include macros/filament.cfg]` — it never had one before. The old klipper-vs-146-only version used bare `G91` to make a retract move relative, which — since it never issued a matching `G90` afterward — left the printer in relative XYZ mode too, not just relative E; routing through `UNLOAD_FILAMENT` (which properly scopes relative mode to just the extruder via `M83` — see the "Relative vs. absolute extrude" note above — rather than touching X/Y/Z mode at all) fixed that as a side effect of unifying. A macro like this — no printer-specific data left once its dependencies are all shared — is a sign it should move to a single plain shared definition rather than being force-fit into the no-op-delegation or engine-plus-wrapper patterns above.

- Each printer's own `printer.cfg`, `moonraker.conf`, `telegram.conf` follow the same per-file conventions described below.

See `README.md` for the full directory tree and the deployment runbook (each host clones this repo to `~/klipper_config` and symlinks `~/printer_data/config` to `~/klipper_config/printers/<hostname>`).

## Relative vs. absolute extrude

Klipper tracks X/Y/Z absolute-vs-relative mode via `G90`/`G91` (`absolute_coord` in `gcode_move.py`), but the E axis has its own override: `M82`/`M83` set `allow_absolute_extrude`, and whenever that's `False` (i.e. `M83` was called), E is forced relative regardless of what `G90`/`G91` last set — `G90`/`G91` alone never touch E's mode once `M83` has been issued. Default state at klippy startup is absolute for both (`G90`-equivalent, `allow_absolute_extrude: True`).

Both printers' slicer (OrcaSlicer, "use relative E distances" enabled for both) emits `M83` near the start of every print body and never switches back — so `M83` is each printer's actual standing convention for the vast majority of a print's runtime, not `M82`. Any macro that runs mid-print (filament load/unload, `M600`, etc.) should leave E in `M83` on exit rather than "restoring" it to `M82`, since `M82` would actually be the _unusual_ state to leave behind. This is why `_LOAD_FILAMENT`/`_UNLOAD_FILAMENT` (see above) deliberately end in `M83`, not `M82`.

A mode change made _inside_ a macro that always runs nested between an active `PAUSE` and its eventual `RESUME` is self-healing regardless: Klipper's built-in `PAUSE`/`RESUME` (`pause_resume.py`) do `SAVE_GCODE_STATE`/`RESTORE_GCODE_STATE`, which snapshot and restore both `absolute_coord` and `allow_absolute_extrude`. This only helps if `RESUME` (not `CANCEL_PRINT`) is what eventually runs, and it's a safety net, not a reason to be sloppy about which mode a macro leaves things in on its own.

## Per-printer files

- `printer.cfg` — main Klipper config: MCU pin mappings, steppers/TMC2209 drivers (klipper-vs-146 also uses `[autotune_tmc]` per stepper), bed mesh, probe, extruder/heater, input shaper, and custom `[gcode_macro]` definitions (print start/end, pause/resume, filament load/unload, bed leveling helpers). Also contains the `SAVE_CONFIG` auto-generated block at the bottom (PID tunes, bed mesh calibration, probe/endstop offsets) — never hand-edit below the `#*# <---------------------- SAVE_CONFIG ---------------------->` marker; Klipper rewrites it. This block is independent per printer.
- `ldo-upstream-printer.cfg` (klipper-v0 only) — the original LDO/Voron installer's full printer template. **Not** referenced by any `[include]` in `printer.cfg` — `printer.cfg` was customized directly instead. Kept only as a reference to diff against upstream; don't assume it reflects live config.
- `moonraker.conf` — Moonraker API server config: CORS/trusted clients, update_manager entries (moonraker-telegram-bot on both; `klipper_tmc_autotune` on both as well). klipper-v0's Moonraker auto-discovers SSL certs at `~/printer_data/certs/moonraker.{cert,key}` (a directory outside this repo) — no explicit `ssl_certificate_path` config needed for that.
- `telegram.conf` — moonraker-telegram-bot config; points at a `secrets.conf` (gitignored, lives on the printer host) for credentials.

## Naming conventions

`temperature_sensor` and fan (`heater_fan`/`controller_fan`/`temperature_fan`) object names are suffixed with their resource type — `_temp` for temperature sensors, `_fan` for fans — even though the section prefix already implies it (e.g. `mcu_temp`, `chamber_temp`, `hotend_fan`). This keeps the name unambiguous when read out of context, such as inside a `SENSOR="temperature_sensor chamber_temp"` string in a macro. Both printers follow this.

## Secrets

Credentials (`secrets.conf`, Moonraker/Fluidd local state, printer host backups like `printer-*.cfg` and `.moonraker.conf.bkp`) are gitignored and kept out of version control — see `.gitignore` (patterns are unanchored, so they match under `printers/*/` too). Never add secrets back into tracked files; reference them via the existing `[secrets]` indirection pattern in `telegram.conf` instead.
