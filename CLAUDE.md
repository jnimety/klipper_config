# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

This is a personal [Klipper](https://www.klipper3d.org/) 3D printer configuration repo for two printers, not a software project. There is no build, lint, or test tooling — changes are validated by restarting Klipper/Moonraker on the printer's host and observing behavior, or by careful manual review of G-code macro logic. There are no automated tests to run.

## Layout

- `printers/klipper-vs-146/` — SKR Mini E3, corexz kinematics, BLTouch probe, Fluidd UI.
- `printers/klipper-v0/` — Voron 0.2 (SKR Pico + LDO Picobilical toolhead board), corexy kinematics, sensorless XY homing, Mainsail UI.
- `macros/` — shared, hardware-agnostic gcode macros and client-macro config (`debug.cfg` / `DUMP_PARAMETERS`, `prime_line.cfg` / `PRIME_LINE`, `print_start.cfg` / `PRINT_START`, `heat_soak.cfg` / `HEAT_SOAK`, `led_indicators.cfg` — no-op defaults for all five `*_INDICATOR` macros, `mainsail.cfg` — see below). Each printer directory has a `macros` symlink to this directory, included as `[include macros/<file>.cfg]`. Only add files here that have zero hardware coupling (no pin references, no printer-specific parking/heating values) — everything else belongs in the printer's own directory; most files here are pure `[gcode_macro]` definitions, but `mainsail.cfg` is the one exception that also carries a few generic, equally hardware-agnostic extras sections (`[virtual_sdcard]`, `[pause_resume]`, etc.) alongside its macros. The two printers' print-end macros are intentionally _not_ unified — they differ enough in hardware to stay printer-local. `PAUSE`/`RESUME`/`CANCEL_PRINT` are unified at the vendor level instead: both printers now include the same vendored `macros/mainsail.cfg` client macro pack — the Alex Zellner `_CLIENT_VARIABLE`-based macro set (runout-sensor awareness, idle-timeout restore, temp restore, configurable park/retract, pause-at-layer; its `RESUME`/`PAUSE`/`CANCEL_PRINT` chain from the `[pause_resume]` built-ins via `rename_existing: RESUME_BASE` etc.) — rather than each hand-rolling its own (it's UI-agnostic — klipper-vs-146 still uses Fluidd as its actual web UI). Genuinely do not hand-edit this file, it's meant to stay a clean copy of the upstream template — upstream is [mainsail-crew/mainsail-config](https://github.com/mainsail-crew/mainsail-config)'s `client.cfg` (the repo renamed it from `mainsail.cfg` in 2023; this repo keeps the old filename since that's already what both printers' includes/docs reference). Confirmed byte-identical to upstream as of the `_CLIENT_LINEAR_MOVE` addition (2024-11-24) — if re-syncing from upstream later, note that this repo's copy does **not** include an `[exclude_object]` section even though an earlier local copy briefly had one; that support now lives as an explicit `[exclude_object]` in each printer's own `printer.cfg` instead (re-copying the file wholesale from upstream is safe and won't lose it). It ships its own extension point instead: a fully-commented-out `[gcode_macro _CLIENT_VARIABLE]` template (with `variable_user_resume_macro`/`variable_runout_sensor`/etc. hooks) that users are meant to copy into `printer.cfg` and customize. Each printer's own `printer.cfg` defines its own **partial** `_CLIENT_VARIABLE` — only the specific variables it needs, not the full template, since every other `client.*` lookup in `mainsail.cfg` already falls back gracefully via `|default(...)` when a variable isn't set: klipper-v0 sets just `user_resume_macro: "RESUME_INDICATOR"`; klipper-vs-146 sets that plus `runout_sensor: "filament_motion_sensor filament_sensor"` (aborts `RESUME` if no filament is detected — this replaced vs-146's old manual `SET_FILAMENT_SENSOR` enable/disable around pause/resume/cancel, which had no equivalent in `mainsail.cfg` and was dropped rather than replicated). Don't copy the rest of the template in without a reason; it'd silently change working `PAUSE`/`CANCEL_PRINT`/park defaults. Never add a same-named `printer.cfg` override of `PAUSE`/`RESUME`/`CANCEL_PRINT` — see the `rename_existing` warning below for why that silently corrupts `mainsail.cfg`'s real logic instead of chaining onto it; use the `_CLIENT_VARIABLE` hooks instead.

  `PRINT_START` and `HEAT_SOAK` are the exceptions — both shared, with any genuinely hardware-specific step delegated to a printer-local macro that the shared one calls unconditionally. `PRINT_START` heats the bed itself (`M190`, generic — both printers have `[heater_bed]`), then calls: `HEAT_SOAK` (waits for the shared `temperature_sensor chamber_temp` to reach `CHAMBER`/`CHAMBER_MINIMAL`, skipped if neither is set above 0 — a pure blocking wait with no timeout, so a target the chamber can't reach will hang the print), `CHECK_BED_LEVEL` (screw tilt probing — real on klipper-vs-146 via its `SCREWS_TILT_CALCULATE`, a no-op on klipper-v0, no probe), and `LOAD_BED_MESH` (loading a saved mesh profile — real on klipper-vs-146, a no-op on klipper-v0, no `[bed_mesh]` configured). New printer-specific steps inside a shared macro should follow this same pattern: call a same-named macro unconditionally, then give every printer an implementation (even if a no-op) rather than branching on printer identity inside the shared file.

  LED status indication follows a public/private split. Public macros are named for what they indicate, not their color — `HEAT_SOAK_INDICATOR` (called from `HEAT_SOAK`), `PRINT_START_INDICATOR` (called from `PRINT_START`), `PRINT_END_INDICATOR` (called from each printer's own `PRINT_END`), `ATTENTION_INDICATOR` (called from any printer-local macro that pauses for manual user input — e.g. klipper-vs-146's `SCREWS_TILT_CALCULATE`/`M600`, klipper-v0 has no equivalent pause point yet), `RESUME_INDICATOR` (called via `macros/mainsail.cfg`'s `user_resume_macro` hook — see above — rather than a same-named `RESUME` override). All five no-op defaults live together in `led_indicators.cfg` regardless of which macro calls them — `PRINT_START_INDICATOR`/`HEAT_SOAK_INDICATOR` are called from the shared `PRINT_START`/`HEAT_SOAK`, while `PRINT_END_INDICATOR`/`ATTENTION_INDICATOR`/`RESUME_INDICATOR` are called from printer-local macros — so this is the one place to look for the full set. Each is safe to call from any printer. Both printers now have a light and override every one of them by simply **redefining the macro** — same section name, no `rename_existing` — to call `_LED_SET NAME=<color> LED=<their light>` — a single **private**, underscore-prefixed, shared entry point (also in `led_indicators.cfg`; the leading underscore is Klipper's own convention for hiding a macro from the web UI's macro panel, signaling "internal helper, not meant to be invoked directly"). Passing `LED=` as a param is what lets this stay a single shared macro instead of a per-printer copy — klipper-vs-146 passes `LED=enclosure` (RGB hardware; the unused `WHITE` component is harmless to pass), klipper-v0 passes `LED=bed_light` (RGBW).

  **Do not add `rename_existing` to these overrides.** Klipper's config loader merges same-named `[gcode_macro X]` sections across every included file into one final section (`configfile.py` builds the parser with `strict=False` specifically so overrides "apply linearly as they do within a single file") — a later block's `gcode:`/`description:` simply overwrite the earlier block's, which is exactly the full-replacement behavior these overrides want, no chaining mechanism required. `rename_existing` only makes sense when overriding a macro that has genuinely distinct content underneath that must still run — and since the same merge applies there too, a second `[gcode_macro SAME_NAME]` block doesn't produce two chainable objects, it collapses into the _one_ merged section Klipper actually loads. Concretely: `rename_existing` only works safely when the name being renamed is a Klipper **built-in** (registered by an extras module — e.g. `PAUSE`/`RESUME`/`CANCEL_PRINT`/`SET_PRINT_STATS_INFO` from `[pause_resume]`, `SCREWS_TILT_CALCULATE` from `[screws_tilt_adjust]`, `BED_MESH_CALIBRATE` from `[bed_mesh]`) — those are registered independently, before any config-file `[gcode_macro]` merging happens, so there's a real separate registration for the override to find at `klippy:connect`. A same-named `[gcode_macro RESUME]` override was tried here once to reset the LED on resume and had to be reverted after redeploying to klipper-v0 exposed the bug: the override's section name collided with `mainsail.cfg`'s real `RESUME` macro, silently discarding its actual resume logic in the merge — not a crash, a silent regression, only caught because that redeploy was the first time this config had ever actually been parsed by Klipper. `RESUME_INDICATOR` is now wired up correctly instead, without a same-named override — via `macros/mainsail.cfg`'s `user_resume_macro` hook, described above.

  Color scheme (deliberately tight — same meaning on both printers): `blue` = actively running (`PRINT_START_INDICATOR`), `orange` = heating/warming up, not a problem (`HEAT_SOAK_INDICATOR`), `yellow` pulsing = needs your attention (`ATTENTION_INDICATOR`), `green` = done (`PRINT_END_INDICATOR`). `red` is intentionally unused by any indicator right now — reserved for a real fault, so it doesn't get diluted by reuse elsewhere (e.g. don't repurpose it for heating or any other non-error state). `off`/`white` remain general-purpose presets in `_LED_COLOR`, not tied to a print-lifecycle indicator.

  `_LED_SET` normally sets a solid color via `_LED_COLOR` (the lower-level macro holding the actual name→RGBW lookup and `SET_LED` call — `_LED_SET` always cancels any in-progress pulse first, then delegates). Pass `PULSE=1` (used by both printers' `ATTENTION_INDICATOR`) for a slow breathing fade instead of a solid color: since gcode macros run synchronously and can't block for the life of a pause, the actual animation lives in `[delayed_gcode _LED_PULSE]`, a self-rescheduling timer (fires every 0.15s, `initial_duration: 0` so it's dormant until triggered) that ramps `_LED_COLOR`'s `BRIGHTNESS` param up and down across a 24-step triangle wave (~7s per full breath) and reschedules itself via `UPDATE_DELAYED_GCODE`. Its state (which LED, which color, current step/direction) persists between ticks in `_LED_PULSE_STATE`, a `[gcode_macro]` used purely as variable storage (set via `SET_GCODE_VARIABLE`, read via `printer["gcode_macro _LED_PULSE_STATE"]`) since `[delayed_gcode]` can't receive params at trigger time. `RESUME_INDICATOR` (solid `blue`, no `PULSE`) cancels any in-progress pulse the same way, so resuming from an `ATTENTION_INDICATOR` pause clears it immediately.

  New status points should follow this same split: add a public `_INDICATOR` macro with a shared no-op default, and let printers with a light override it — by plainly redefining the same-named macro, **not** `rename_existing` — to call `_LED_SET NAME=... LED=...` (adding a new color preset is a one-line dict entry in `_LED_COLOR`, shared by every printer) — never call `SET_LED` or `_LED_COLOR` directly from a public macro.

- Each printer's own `printer.cfg`, `moonraker.conf`, `telegram.conf` follow the same per-file conventions described below.

See `README.md` for the full directory tree and the deployment runbook (each host clones this repo to `~/klipper_config` and symlinks `~/printer_data/config` to `~/klipper_config/printers/<hostname>`).

## Per-printer files

- `printer.cfg` — main Klipper config: MCU pin mappings, steppers/TMC2209 drivers (klipper-vs-146 also uses `[autotune_tmc]` per stepper), bed mesh, probe, extruder/heater, input shaper, and custom `[gcode_macro]` definitions (print start/end, pause/resume, filament load/unload, bed leveling helpers). Also contains the `SAVE_CONFIG` auto-generated block at the bottom (PID tunes, bed mesh calibration, probe/endstop offsets) — never hand-edit below the `#*# <---------------------- SAVE_CONFIG ---------------------->` marker; Klipper rewrites it. This block is independent per printer.
- `ldo-upstream-printer.cfg` (klipper-v0 only) — the original LDO/Voron installer's full printer template. **Not** referenced by any `[include]` in `printer.cfg` — `printer.cfg` was customized directly instead. Kept only as a reference to diff against upstream; don't assume it reflects live config.
- `moonraker.conf` — Moonraker API server config: CORS/trusted clients, update_manager entries (moonraker-telegram-bot on both; `klipper_tmc_autotune` on both as well). klipper-v0's Moonraker auto-discovers SSL certs at `~/printer_data/certs/moonraker.{cert,key}` (a directory outside this repo) — no explicit `ssl_certificate_path` config needed for that.
- `telegram.conf` — moonraker-telegram-bot config; points at a `secrets.conf` (gitignored, lives on the printer host) for credentials.

## Naming conventions

`temperature_sensor` and fan (`heater_fan`/`controller_fan`/`temperature_fan`) object names are suffixed with their resource type — `_temp` for temperature sensors, `_fan` for fans — even though the section prefix already implies it (e.g. `mcu_temp`, `chamber_temp`, `hotend_fan`). This keeps the name unambiguous when read out of context, such as inside a `SENSOR="temperature_sensor chamber_temp"` string in a macro. Both printers follow this.

## Secrets

Credentials (`secrets.conf`, Moonraker/Fluidd local state, printer host backups like `printer-*.cfg` and `.moonraker.conf.bkp`) are gitignored and kept out of version control — see `.gitignore` (patterns are unanchored, so they match under `printers/*/` too). Never add secrets back into tracked files; reference them via the existing `[secrets]` indirection pattern in `telegram.conf` instead.
